## What this repo is

A patch overlay on [kineticman/FastChannels](https://github.com/kineticman/FastChannels) `main` (his release branch, so every build is released code). **One exception:** on 2026-10-08 a single build from his `development` (`b71954d`) was published as `:latest`, because the trimmed patch needs his new code sign-in (`directv_device_auth.py`), which is only on development so far. Builds can be published from development again with a manual run with `upstream_branch=development` and `publish` ticked. Until his `main` has that file, scheduled `main` builds skip quietly (a check in `build.yml`'s skip step), with no failure and no AI repair, and `:latest` stays on that development build. CI applies `patches/` to upstream, validates, builds, smoke-tests and boot-tests the image, and publishes `ghcr.io/mackid1993/fastchannels-mackid1993:latest` (public; pulls need no login). Builds and publishes every ~6 hours when upstream `main` changes (a push just reruns the tests — `:latest` rebuilds only on a real upstream/APK/patch change), watches upstream `development` to fix drift early into held PRs that `reconcile-drift.yml` auto-merges once valid against `main`, and does fire-and-forget AI repair with Aider on Anthropic's API (since 2026-10-09: `ANTHROPIC_API_KEY` secret, paid from David's Claude Max monthly API credit; the model is the `AI_MODEL` variable and the workflow default, Claude Haiku 5.5, `anthropic/claude-haiku-5-5`, checked end to end by `model-preflight.yml`, which also runs a real Aider edit. Before that it was GLM 5.3 Flash on OpenRouter; an `openrouter/<id>` model with an `OPENROUTER_API_KEY` secret still works). The AI handles both a patch **conflict** (the `resolve` job) and **drift** — the patch applies but a check then fails because upstream renamed/moved something (the `resolve-drift` job, on scheduled and development-watch runs); both auto-merge only after the fix passes the full gauntlet, and `open-pr`/`ai-failed` report the outcome. The behavioral relay tests in `smoke_test.py` are the guard that an AI (or human) fix keeps the DAI behavior, not just the hook strings. The patch refreshes its own context (`patches/` + `source/`) after every successful run, so upstream drift rarely turns into a conflict.

**The overlay touches upstream in exactly one line**: `from .scrapers import directv_dai_install; directv_dai_install.install(app)` before `create_app` returns in `app/__init__.py`, inserted by `scripts/insert_hook.py` (not a patch hunk, so it can't conflict). `patches/` only adds the overlay's own files. `directv_dai_install` attaches everything at runtime, keyed on as few upstream internals as possible. See "Where the hooks live" below.

## Why this exists: fairness, not features

The DAI patch exists so this setup treats DirecTV and its advertisers fairly, not to get a better picture or to dodge anything. A paying subscriber should watch the way DirecTV intends, with each party getting its fair share:

- **DirecTV and the networks** get their ad inventory filled and counted through their own ad-insertion system, instead of local ad slots sitting empty or showing filler.
- **Advertisers** reach the market they paid for (the account's real DMA), with the ads delivered and counted.
- **The subscriber's choices are respected.** `is_lat` follows the playback device's own ad-tracking setting, the way DirecTV's TV apps do it (the Osprey reads it from the device, not the account's web consent). A device that limits ad tracking sends the apps' opted-out form. When the requester isn't a known bridge device, the account's GPP consent decides.
- **We tell the truth about ourselves.** Every value is either the account's own data or DirecTV's own published client value for an Android TV client. Nothing is invented, and nothing is logged that shouldn't be. The one exception, by David's choice (2026-10-09): the client identity, meaning the User-Agent and `comscore_device`, matches upstream's single fixed app identity (a Chromecast) rather than each box, so the whole session shows one consistent client.

When changing this code, keep that goal ahead of convenience:
- If you don't know the correct value, leave it out rather than guess.
- Don't impersonate another client or device beyond the Android TV identity DirecTV's own app uses.
- Don't sign in as another app.
- Don't send fabricated ad-view or measurement data.
- Don't do anything to skip or suppress ads.

## User-Agent: the app's real string (and why not `Custom-Exoplayer`)

Before 2026-10-01 the relay sent python-requests' UA on the bridge master fetch (the request that opens the Yospace session) and a Windows Chrome UA on playlists and segments. On 2026-10-01 both were briefly switched to `Custom-Exoplayer`, the string hard-coded in DirecTV's Android TV `ExoPlayerWrapper`. Side by side on CNN (same account, same URL, only the UA differed), the old UAs got inserted ads at 23:53 and 23:55 and the `Custom-Exoplayer` session got none. Reverted. That string is only the app's non-Cronet fallback; with Cronet (`CRONET_LEVEL = 2`) the app's player sends the native `AnalyticsService::generateUserAgent()` string: `APP_PROJECT_NAME/<app version> (<OS name> <OS version>; <Build.MODEL>; <Build.BOARD>)  PureRN/0.79.5` (literal `APP_PROJECT_NAME`, two spaces before `PureRN`). Any UA change must be A/B tested for inserted ads first.

From 2026-10-02 the patch sent that real app string (A/B tested 2026-10-02: inserted ads in the same breaks as the old UAs, 8 each), built per bridge device from `getprop ro.build.version.release`, `ro.product.model` and `ro.product.board` (a Fire TV Stick 4K Max: `APP_PROJECT_NAME/5.0.136.2002113867 (Android 11; AFTKRT; karat)  PureRN/0.79.5`).

**Since 2026-10-09 the relay and the DAI authorization send upstream's own fixed app string instead**, `directv_device_auth.APP_USER_AGENT` (`APP_PROJECT_NAME/5.0.136.2002113867 (Android 12; Chromecast; sabrina)  PureRN/0.79.5`, role `app_user_agent`), still only for requests from a bridge device. David's call: upstream's sign-in, refresh and DRM calls already send that one string, so the session shows DirecTV one client that never changes instead of two (Chromecast on the account calls, each box's own on playback), and the overlay stays consistent with upstream. `comscore_device` follows it, also David's call (matching upstream's one client matters more than naming the real box): it names the device that User-Agent presents, `Android_Google_Chromecast` (`directv_dai_device.presented_device()` reads model and board from upstream's string; `_UA_MANUFACTURERS` maps the board to `Build.MANUFACTURER`). If upstream's string ever names a board not in that map, `comscore_device` falls back to the box's real values, the smoke test fails, and `status()['failed']` (red in the DAI panel) names it at runtime. The device ad id, `is_lat` and every other flag are unchanged. The overlay's own account lookup (market/ZIP/consent, `fetch_account_context`) sends the same app headers with no web `Origin`/`Referer`, and a bridge box gets the app User-Agent as soon as it's recognized, without waiting for its adb identity read. What's left that isn't the Chromecast is upstream's own refresh form (`clientMake=Google`, `clientModel=Chrome`) and the TLS handshake of Python's HTTP client, neither of which the overlay can change. **Confirmed live 2026-10-09** (CNN on box .17, after a cache bust: User-Agent and `comscore_device=Android_Google_Chromecast`): inserted ads still fill, the same ones as before. If a break ever comes back empty, revert `directv_dai_device.player_user_agent()` and `presented_device()` to the per-device values (git history before 2026-10-09). Sources: `AnalyticsService::generateUserAgent()` (literals `APP_PROJECT_NAME`, `/`, ` (`, ` `, `; `, `) `, ` PureRN/`, then 0.79.5), `DeviceInformation::getDeviceOSName()` = `Android`, `getAppVersion()` = `JManifestInfoProvider::getVersionNumber()` = the package versionName, and `Java_com_clientapp_cronetservice_CronetHttpService_getUserAgent` = `AnalyticsService::getInstance()->getUserAgent()`, which Cronet sends because `CustomCronetDataSourceFactory` never sets its own UA.

## Removed: stereo downmix (`dtv_stereo_downmix`, deleted 2026-10-03)

The "Downmix DirecTV audio to stereo" toggle declared DirecTV's AC-3 rendition `CHANNELS="2"` in the proxied master so the stick's media3 would emit AC-3's Lo/Ro fold instead of its own. **Deleted as flawed.** The segments are still 5.1 AC-3, so declaring 2 channels is a manifest/bitstream mismatch — it forces media3 (notorious for poor 5.1→stereo handling) into a **thin** fold (live A/B on box 16: `"2"` was ~2 dB brighter but hollow vs the stock `"6"`; the user heard it as thin). Its only real purpose was a loudness lift, which the inserted-ad cut (`dtv_aac_gain`) now covers. **A proper 5.1→2.0 downmix can only run on decoded PCM** (Lo/Ro matrix, LFE dropped), and since the content AC-3 is DRM-encrypted and DirecTV ships a 5.1-only rendition (no native stereo), that can only happen on the stick/player (media3 `ChannelMixingAudioProcessor`), never in the relay. Not worth the APK change: the AC-3 is left **stock** (`CHANNELS="6"`, the honest declaration), and loudness is set with the LinkPi/receiver gain (the user runs +6, sounds great). Fully removed: the module, the `stereo_downmix` toggle, the `config_schema` + `directv_browser_manifest` hooks, the UI toggle, and the `validate.sh` guards; `smoke_test.py` asserts none of it returns. (History: this was the old `keep_surround` downmix, added/reverted a couple of times 2026-10-02; now gone for good.)

Upstream merged the Android TV code sign-in into `development` on 2026-10-08 (not yet in `main`) as `app/scrapers/directv_device_auth.py`. It is kineticman's port of this overlay's `dtv_android`: the `UNIFIED_Android_TV_02` device-code grant, approved once at directv.com/tvsigninv2, and `authn-refreshgo` refresh with `reqParams=ACTIVATIONTOKEN`, which re-mints the DRM activation token. He also added `apply_auth_result`, `can_reauth`, and "Sign in with a code" and "Sign out" buttons, and kept email/password as a fallback. So the overlay **no longer carries any sign-in, refresh, token-staleness or DRM-recovery code**. `dtv_android.py` is gone, and the full old version is in `archive/android-tv-client-before-upstream-merge/` (git tag `pre-dai-only-trim`).

Upstream's version differs from the old overlay in a few ways. Its sign-in, refresh and DRM requests send one fixed app User-Agent (`APP_PROJECT_NAME/… (Android 12; Chromecast; sabrina)`), not each device's own. It has no single-flight DRM self-heal: `_directv_trigger_reauth` drops the activation token and queues a refresh. It refreshes on its `_TOKEN_TTL` (75 min) staleness check in `pre_run_setup`. And it has no viewer-profile picker, which the overlay keeps (see "Viewer profiles"). The overlay keeps only what DAI needs on top:
- `directv_device_auth._result` is wrapped so the grant's `valuePairs.partnerProfileId` (the Yospace `hhid`/`u`) survives into the login result. Upstream keeps only the activation token from `valuePairs`.
- `apply_auth_result` is wrapped so every sign-in and refresh also runs `directv_dai.store_login_result`. With DAI on, that fetches the account's DMA, ZIP and GPP with the bearer for a `device_code` session (with DAI off, sign-in makes no extra requests; turning DAI on fetches them then, `settings_changed`).
- A session the old overlay signed in (`auth_method: 'dtv_android'`, the same grant client) is re-tagged once to upstream's `AUTH_METHOD` (`install.migrate_old_sessions`, at startup or the first request), so upstream refreshes it. Nobody has to sign in again. (This replaced a wrap of `is_device_session` on 2026-10-08.)
- The profile picker is kept (see "Viewer profiles"). Upstream's logout leaves `dai_*` and `dtv_android_profid` alone, so a chosen profile survives a sign-out and sign-in.

## channel/v2 (the Android TV app's endpoint)

The Android TV app's bundled config authorizes channels on `right/authorization/channel/v2` (the web uses v1). Same query params; the response has `playbackData.streamUrls: [{groupName: 'DAI'|'Data Center', URLs: [...]}]` and the same `dRights.playToken`. Measured 2026-10-02 on CNN: v2's DAI URLs had the same Yospace host, path and parameter names as v1's `streamURL` (one identical after masking tokens). With DAI on the patch uses v2 to match the app (`directv_dai_install._fetch_dai_playback`, our own request in place of upstream's `_fetch_channel_playback` for that tune). The app adds `hevc`/`maxHevcLevel`/`maxAvcLevel`/`hdr`/`deviceModelIdentifier` only when its remote `dualEncodeEnabled` flag is on; not sent.

## Android TV authorization request

With DAI on, `directv_dai_install._fetch_dai_playback` drops the web player's `Origin`/`Referer`, sends the device's app User-Agent, and sends the app's query: `ccid`, `proximity`, `reserveCTicket=true`, `daiEnabled=true`, `startOver=false`, `abrEnabled=true` (from `getQueryParams` in the app bundle; the web-only `timeShiftEnabled` and `dualManifest` are dropped). `clientContext` is sent only when the session has one; the code sign-in never captures one. An expired token raises upstream's own `DirectvAuthExpiredError`, so upstream's re-auth runs. Any other failure falls back to upstream's v1 request, so DAI degrades to off and the tune still plays. Tested 2026-10-02: 200, authorized, play token present, same Yospace host and identical DAI URL parameter set as the web request.

## Viewer profiles

A DirecTV account has several viewer profiles, like Netflix. **The picker matters for ad targeting**: the Yospace `profid` is the chosen profile's id, and the code sign-in's grant carries no profile id. Without the picker, `profid` is never sent.

Source settings show a **Run as DirecTV profile** picker whenever the source has a code sign-in session. `GET /api/sources/<id>/directv-profile` lists the profiles (`directv_dai.list_profiles`, a read-only GET with the account bearer). Selecting one `POST`s to the same route, which calls `directv_dai.select_profile`. That runs the app's profiletoken exchange (`profile_token_exchange`), stores the returned `partnerProfileID1` as `dtv_android_profid` (the key name is historical; `build_query` reads it), and clears the cached Yospace playback.

The account session (bearer, refresh, activation) is left untouched, as the app does; only `profid` changes per profile. The exchange is single-flight behind upstream's own refresh lock, `directv:auth:refreshing:<name>`, so a concurrent refresh can't race it. It takes the lock with its own value and releases it only if still its own (atomic Lua compare-and-delete); the result is merged with `persist_config` (so a token written during the exchange survives); and afterwards, whether the switch succeeded or failed, if the session went stale while it held the lock (upstream's re-auth would have skipped as "in progress"), it queues upstream's refresh itself. The client id is upstream's `directv_device_auth._CLIENT_ID` by role (`code_signin_client_id`), with no fallback. The route is in `directv_dai_install`'s blueprint, and the picker is part of the DAI panel (see "Where the hooks live"). `profid` is omitted when unknown (fairness rule). (Briefly dropped by mistake in the 2026-10-08 trim and restored the same day; `smoke_test.py` now guards it.)

## Hardening from the 2026-10-09 three-angle review

- **profid is always sent.** It is only ever the picked profile's `partnerProfileID1` (a sign-in's `profileId` is the profile-manager id, never sent). With none picked, the account's **default (primary) profile** is picked automatically (`_auto_pick_profile`, via `select_profile`) after sign-in, on DAI turn-on, and from a tune that finds none (rate-limited, 5 min); a panel pick is never replaced. A tune without profid shows red in the panel (`no_profid`).
- **Cached sessions must match current targeting.** Each DAI session stores `dai_targeting`, the ad-deciding values it was opened with (hhid, profid, DMA, GPP, ZIP, device id, adid, is_lat). `resolve` and the per-box store drop a session only when a value known now is missing from it or differs (opened before the ZIP/profile arrived, or under another account); a value this process can't know yet (another worker's unsaved ZIP) never makes it stale. The check is read-only.
- `device_ad_flags`, the billing DMA lookup, the Google TV Ads-screen read and the channel/v2 request (User-Agent, 15 s timeout) are unchanged from the proven code. Reviewer suggestions to change them (opt-out ordering, billingDmas source, app UA for non-bridge requesters, shorter timeout, hourly Fire id re-read, detached GMS read) were reverted on 2026-10-09: proven, live-verified behavior is not changed on speculation.
- Stability: the bridge-device list is also kept on disk (`directv_dai_bridges.json`), so every gunicorn worker and each recycled worker recognizes boxes without waiting on ah4c; device identity re-checks are stamped (`checked_at`), so recycles don't re-run adb. The Google TV Ads-screen read is the proven, live-verified script, unchanged: it reads the screen, so it must run in the adb session, never detached (a 2026-10-09 detached version was reverted). One capture per box across workers (redis). A rotated refresh token from a profile switch is re-read after saving (upstream's commit retry can report success after a rollback), and the profile lock covers the worst case (600 s). The per-box session store is merged into the fresh row in the background, under the overlay's own cross-process lock, reading only that key. Ad segments are capped at 2 MB. File locks are polled (never a blocking flock in a gevent worker). (No proxy warning: upstream's ProxyFix already resolves the client address from X-Forwarded-For, so boxes behind one proxy are recognized; a 2026-10-09 `proxied` warning was removed as a false alarm.)

## Stable device ids

Every session uses the device's saved values from `/data/directv_dai_devices.json` (`app/scrapers/directv_dai_device.py`) (keyed by adb address): one stable identity per device, even when it's asleep or adb is down. A new device is read over adb on first sight, in the background with up to ~4 s wait so its first session already carries its identity (a stuck adb never holds a request longer), and saved. The request IP → bridge address lookup reads upstream's device list (`known_devices`, which asks ah4c over HTTP, up to 5 s when ah4c is slow). Since the relay checks it on every segment, the **list** is cached (2026-10-09, `directv_dai_device._read_bridge_devices`): reads run in the background one at a time with no lock held across them; after the first read a stale list is served while a refresh runs (60 s); upstream **returns** ah4c's error rather than raising (`known_devices() -> (devices, ah4c_error)`), so on an error the last good ah4c tuners are kept merged with the database's devices, a warning is logged once, and unknown requesters stop triggering reads for 60 s; otherwise an unknown requester starts at most one read per IP per 10 s and waits at most 1.5 s. A slow or dead ah4c never stalls a recognized box. Known devices are re-checked in the background about hourly; only a real change (a factory reset's new Android ID, an ad-tracking toggle, firmware) updates the saved values, logged as `[directv-dai] device <addr> changed (...)`. Failed re-checks are ignored. Nothing to do by hand. History: before 2026-10-02 a failed read cached `{}` for an hour, sending sessions with no device id (account consent, mostly national spots). (This file holds device **identity** only; the device's **advertising id** is captured and stored separately — see "Advertising-id capture".)

## Advertising-id capture (the real GAID the app sends)

Added 2026-10-04. The DirecTV Android TV app sends the playback device's **real platform advertising id** (`google_advertising_id:<id>` + `adid`) with `is_lat` from the device's own ad-tracking choice. We now match that per bridge device, read the way each platform exposes it, instead of the uniform `android_id` the overlay sent before (a 2026-10-02 decision made only because a Google TV's GAID looked unreadable over adb — now narrowed to the fallback):

- **Fire TV / Fire OS** (the production fleet is all Fire TV Stick 4K Max, AFTKRT): `settings get secure advertising_id` returns the real UUID silently (Amazon mirrors it to Settings.Secure); `limit_ad_tracking=1` is the opt-out. No screen, no app. Verified live: real UUIDs on the production sticks.
- **GMS (Google TV / plain Android with Play Services)**: the GAID is locked to an app process — **not** in settings, not in any `dumpsys`, and a shell **cannot** bind the GMS ad-id service (ActivityManager refuses a non-app caller; an `app_process`/dex read dies on `Unable to find app for caller`, a no-root wall — confirmed, not a code bug). The only root-free read is the device's own **Ads settings screen**: open `com.google.android.gms.settings.ADS_PRIVACY`, read the id off the uiautomator view hierarchy, restore HOME. Verified live on an onn 4K (Google TV): reliable, ~**3 s** on-screen flash, `STATE=active|deleted`. That flash is why it is a **one-time** read.
- **Neither** → fall back to `android_id:<ANDROID_ID>` (the prior behavior), the **absolute last resort**. An all-zero id is the deleted/limited sentinel → the opt-out form, never sent as a real id.

**Capture once, trust it, never on a schedule, never at a tune.** The id is captured once per device and persisted to `/data/directv_dai_adids.json` — a **separate** store from `directv_dai_devices.json`, so the hourly device-identity re-read (`directv_dai_device`) can't clobber it. It is **never** re-read on a timer, and a **tune never captures** (a GMS screen read would interrupt the tuning box). Capture runs only from an explicit action: turning DAI on in the DAI panel (`settings_changed` → `clear_cache_if_toggled`) captures every bridge device that has no id yet, and an admin **"Capture advertising IDs"** button (shown only when DAI is on and a box still needs one) does the same on demand. A box that is **currently playing is skipped** (`_is_playing` — a media session in STATE_PLAYING or a started media audio player; screensaver/asleep is idle; fail-safe: on any doubt, treated as playing), so a stream is never interrupted — re-run when it's idle. To force a fresh capture of all boxes: toggle DAI off and on (or delete `directv_dai_adids.json`). DAI needs the **AH4C bridge** (an Android device); it does nothing on Prismcast. The toggle's help text discloses the one-time read (silent on Fire TV; a brief Ads-screen flash on Google TV, skipped while playing). The `directv_dai_adids.json` read-modify-write is guarded by a thread lock **and** a cross-process `flock` (`_adids_file_lock`), because the app runs several gunicorn workers and two workers capturing at once would otherwise interleave and lose an entry. A capture that stores a new id **busts the DirecTV source's cached stream URLs** (`_bust_playback_cache`), so the next tune actually sends the new id instead of a cached URL carrying the old one (`cached_url_usable` also refetches on an id mismatch; the bust closes the window explicitly).

Lives in `directv_dai.py` (`capture_registered_devices` → {captured, playing, unreachable, none} — the button's result text distinguishes these, `capture_in_background` carrying the Flask app context into its thread, `uncaptured_addresses`, `_capture_and_store` single-flight, `_reachable` (a fast adb check so a powered-off device reads as unreachable, not no-id), `_capture_one`, `_read_fire_advertising_id`, `_read_gms_advertising_id`, `_is_playing` the playback gate, `_GMS_CAPTURE_SH`, the `_adids_file`/`_saved_adids`/`_save_adids`/`_store_adid`/`_adids_file_lock` store, `_bust_playback_cache`, and `device_ad_flags(props, ad_id)`), plus the `directv-capture-adids` route and the button, both in `directv_dai_install` (its own blueprint and the DAI panel). No template or route file of upstream's is edited. `directv_dai_device` reads only device identity, never the ad id. Fairness holds: every value is the device's own real id or an honest opt-out; nothing is invented.

## Where the hooks live

The goal is that upstream changes break the overlay as rarely as possible, and loudly when they do. So it depends on as few of kineticman's internals as it can, and on the most stable ones.

**One line in upstream**, before `create_app` returns in `app/__init__.py`: `from .scrapers import directv_dai_install; directv_dai_install.install(app)`. `scripts/apply-patches.sh` runs `scripts/insert_hook.py`, which finds `create_app` with Python's parser and inserts the line before its `return app`, wherever upstream moved it. It is not a patch hunk (`refresh-patches.sh` leaves `app/__init__.py` out), so `git am` has no upstream context to conflict with: the patch only adds our five files. `validate.sh` checks mechanically that upstream's files differ by that line and nothing else.

**Everything else is in `app/scrapers/directv_dai_install.py`**, in three layers, most stable first:
- **HTTP layer (no upstream function names).** A Flask `after_request` swaps inserted AC-3 ads to their AAC twins in every playlist response under `RELAY_PREFIX` (`/play/directv/`). A `before_request` serves inserted-ad AAC segments there with the loudness cut (only on hosts in upstream's own DirecTV CDN allowlist; the relay is never an open proxy). The app User-Agent is added on `requests.Session.request` for relay fetches (in a `/play/directv/` request, to an allowlisted host, with DAI on, from a bridge device). Upstream can restructure its relay code freely.
- **Our own UI.** The DAI toggle, profile picker and "Capture advertising IDs" button are our panel (`_ADMIN_JS`), saved through our own route (`/api/sources/<id>/directv-dai`). Its POST routes take JSON only (like upstream's), so another website's form can't flip DAI or trigger a capture. An `after_request` adds the script to upstream pages that have source settings boxes (`id="source-config-<id>"`); the script puts the panel inside the DirecTV source's box. The same panel is on its own page at `/directv-dai`, which works even if upstream rebuilds its settings page. `use_dai` is not in upstream's `config_schema`; upstream's settings save keeps keys it doesn't know (smoke-tested).
- **Wrapped by name (unavoidable).** `TARGETS`: the tune path (`DirectvScraper.resolve`, `_fetch_channel_playback`, `prepare_license_request`), the lineup rows, `apply_auth_result`, `directv_device_auth._result`, and the CDN allowlist tuple. `USES` lists every other upstream name the modules call or read (`known_devices`, `persist_source_*`, `Source`, `db`, ...). `SOURCE_MARKERS` lists upstream strings relied on (the settings-box id, the refresh-lock key). `TARGETS`/`USES` are keyed by a fixed role; the overlay and `smoke_test.py` look upstream up only by role (`up(role)`), so a rename upstream is a one-line change of that role's value and the tests follow it (before 2026-10-09 the smoke test hard-coded his names, so even a correct AI rename fix failed it). `AGENTS.md` has the table.
- **AI repair provider.** `scripts/openrouter_provider.py` gives every AI call its model settings: an output budget for an `anthropic/` model (Anthropic requires `max_tokens`), provider routing for an `openrouter/` one, and which key each needs. For OpenRouter: OpenInference ignores the file contents in Aider's request (the model answers that no files were added), which is why the 2026-10-08 rehearsals failed. `scripts/openrouter_provider.py` routes every AI call away from it (DeepInfra first; override with `AI_PROVIDER_ORDER`/`AI_PROVIDER_IGNORE`).

Each hook runs upstream's behavior untouched when DAI is off, and falls back to it on any error. Module-level wraps are applied once per process, since `create_app` runs several times (the web app, the worker, `run_directv_auth`); per-app hooks once per app. Breakage is reported, never silent:
- `validate.sh` (before any image): upstream files changed by the one line only; every `TARGETS`/`USES` name, `SOURCE_MARKERS` string and the `RELAY_PREFIX` route present; the panel script mounts before `config-actions` in a stub DOM.
- `smoke_test.py` (in the image): each wrap applied exactly once; a wrap whose target changed shape (a renamed fetch argument, `prepare_license_request` no longer a classmethod) is in `status()['failed']`; the DAI request carries the bearer and returns upstream's playback keys; the relay is driven through upstream's real routes with the network stubbed at the `requests` transport; a tune that bypasses our fetch is reported; and end to end on a throwaway database (the panel route, upstream's save keeping `use_dai`, the old-session re-tag, the real sources page). The roles the overlay only reads are checked by what they do in upstream, not just by name (since 2026-10-10): the session lifetime is the age limit upstream's `resolve()` applies to its cache, the client id is what its code sign-in sends, and the three refresh roles are what its `pre_run_setup` calls. So a rename fix, human or AI, that points a role at a look-alike fails and names the role, instead of passing and quietly changing behavior. Verified by pointing each role at a wrong name on purpose: every one failed.
- `smoke_test.py` also reads upstream's routes, source name and stream-URL format from `CONTRACT` in `directv_dai_install.py` (checked against the running app; the AI repair can update them), tests the profile switch against upstream's real refresh-lock key, and checks our channel/v2 request for parity with upstream's v1 request (parameters, headers, expired-token signals). The allowed differences are `CONTRACT`'s `web_only_params`/`web_only_headers`/`app_only_params`; a new upstream value goes on a web_only list unless the Android TV app is known to send it (fairness: never copy a web value into the app request).
- At runtime, the DAI panel shows a red list from `status()` (`/directv-dai/status`): missing names or strings, failed wiring, and **runtime** problems: DAI is on but the newest tune didn't get a DAI stream (`bypassed`, `error`, `fallback`, newer than the last good DAI tune), or an inserted ad went out without the loudness cut (`ad_uncut`: its host isn't relayed, or it didn't parse; newer than the last cut ad). Kept in redis (7-day TTL) so every worker sees it, and shown only while DAI is on. Because every hook falls back to upstream, this is what makes a silent "DAI quietly off" visible.

**Per-device DAI sessions.** Upstream caches one playback entry per channel, but each box needs its own Yospace session (its device id is in the URL). So each box's DAI session is also kept per box (`DEVICE_SESSIONS`, cache key `dai_playback_by_device`, tied to the current bearer, 1 h): a box re-tuning a channel another box tuned since gets its own session back instead of a new authorization, and its license request (the `prepare_license_request` wrap) carries its own session's play token. Everything that clears `directv_playback` clears these too. A box's session lives exactly upstream's `_PLAYBACK_CACHE_TTL` (role `playback_cache_ttl`, 3300 s), never longer, so its license never carries a play token upstream would already have refetched.

If upstream renames something, fix the reference in `directv_dai_install.py` (and the module that uses it); never edit upstream's file. The device list is read in one place, `directv_dai_device.known_bridge_devices()`. `test-development.yml` runs the whole gauntlet against his `development` on every push here and whenever `upstream-watch.yml` sees a new development commit, so a break shows up before his release.

## Removed: one DRM session through inserted ads (keep_drm_session)

`keep_drm_session()` dropped Yospace's `#EXT-X-KEY:METHOD=NONE` so FC Player kept its secure decoders through ads (like the Android TV app's `setUseDrmSessionsForClearContent`). Tried, briefly re-added, and **reverted for good on 2026-10-02 because it reduced ad targeting** — dropping the `METHOD=NONE` marker changed the session enough that breaks came back with less-targeted (national) fill. It never changed the ad audio anyway (that's in DirecTV's per-creative AC-3 files; see the 7 kHz findings). The audio fix is the AAC swap below.

## Inserted-ad audio: the AAC swap (`app/scrapers/dtv_aac_ads.py`)

Many inserted-ad creatives are band-limited (~7 kHz) in their AC-3 rendition while the *same* creative's HE-AAC twin is full range — upstream and the Osprey play the same AC-3 files, so no flag, header or identity changes which file is served. `swap_muffled_ads()` (its own module, run by `directv_dai_install`'s `after_request` on every DirecTV playlist the relay serves) rewrites each inserted ad on the DAI AC-3 audio playlist — every segment **and** the ad's own `#EXT-X-MAP` init, matched by the Yospace ad-creative name `u-<id>-c-<rate>-…mp4` on the ad CDN — to the `-a-96-` HE-AAC twin. Yospace emits the ad's MAP itself, so it's a pure URI rewrite; live `dfwlive-*` content never matches (channel audio untouched), and it's a safe no-op on any other playlist. The clear ads keep `METHOD=NONE`. Trade-offs: swapped ads play **stereo** (the AAC twin is 2.0), and *every* inserted AC-3 ad is swapped (every measured AAC twin was full range, so there's no per-ad muffle detection in the request path). Consistent with the fairness rules — same creative, DirecTV's own rendition, delivered and counted the same. **Confirmed working 2026-10-03** (David reports DAI + loudness "working beautifully"; swapped breaks play clear, not silent). If a swapped ad ever comes out *silent* rather than muffled, FC Player didn't accept the AAC twin's init.

## Inserted-ad loudness: the −12 dB AAC gain cut (`app/scrapers/dtv_aac_gain.py`)

The AAC-swapped ads play much hotter than the programming. On the bridge's actual LinkPi feed (box 16, measured 2026-10-03) the AC-3 programming (stock 5.1, folded to stereo by the stick) sits at ~**−32 to −36 LUFS** while the inserted AAC ads measure ~**−20.6** — ~11–15 dB hotter. (This is a *relative* gap; the absolute level is normal for dialnorm-referenced decoded AC-3 and sounds plenty loud — see the Audio findings. Don't recalibrate the cut to chase an absolute target.) `attenuate_ad_segment()` (its own always-on module; `directv_dai_install`'s `before_request` serves inserted-ad AAC segments on the relay itself, cut, while everything else goes to upstream's view) pulls each inserted AAC ad down to match — losslessly, no re-encode: it edits each HE-AAC frame's `global_gain` down `_DEFAULT_STEPS` steps (1.5 dB each; currently **8 = −12 dB**, so a break lands at ~−32.6). Each segment logs the dB applied at DEBUG (an inserted ad that goes out un-cut logs at INFO), so re-tuning against a live ad is one constant (`_DEFAULT_STEPS`). **The ad twins are HE-AAC 48 kHz stereo** (the low-bitrate `u-6600-a-96` rendition; a codec probe's object-type field can read as plain low-complexity AAC and mislead — these are HE-AAC, do not relabel them). **No toggle; implicitly DAI-gated** — it only matches the `u-<id>-a-96-<n>-<n>.mp4` twins the swap creates, never live `dfwlive-*` content, and no-ops on the `-i` init. It's an original implementation of the ISO/IEC 14496-3 HE-AAC bitstream (the Huffman + scalefactor-band tables are the standard's data — no third-party code), walking SCE/CPE `raw_data_block`s including the full channel-1 spectral skip needed to reach a stereo CPE's channel-2 `global_gain`, parsing the fMP4 `moof/trun` for per-frame sizes, and auto-detecting the sample rate. **Safety:** it edits only if every frame parses cleanly to `END` at one rate; on any mismatch it returns the bytes unchanged, so it can never emit a corrupted segment. Verified live 2026-10-03: `attenuated 284 frames @ 48000 Hz` on every ad segment of a CNN break (no Range-skip, clean HE-AAC). Consistent with the fairness rules — DirecTV's own creative, delivered and counted the same, just at the right level.

## The DAI patch in one paragraph

The opt-in "Use DirecTV ad insertion (DAI)" toggle makes DirecTV playback use `streamURL` (a Yospace server-side ad-insertion session) instead of `fallbackStreamUrl`, adds `yospace.pool=livepause` (Yospace answers 503 without it), and adds the ad flags DirecTV's own Android TV app sends. The authorization request (`channel/v2`, app query, no browser headers) and the relay's User-Agent match the Android TV app too. The ad-insertion logic lives in `app/scrapers/directv_dai.py`, the bridge device's identity and app User-Agent in `app/scrapers/directv_dai_device.py`, the runtime wiring in `app/scrapers/directv_dai_install.py`, the inserted-ad AAC swap in `app/scrapers/dtv_aac_ads.py`, and the inserted-ad loudness cut in `app/scrapers/dtv_aac_gain.py`. Upstream gets one line (see "Where the hooks live").

**`yo.lpa` dropped 2026-10-03 (confirmed):** removed `yo.lpa` from the sent flags because it's an Osprey-config flag the Android TV app does **not** send (off-profile for our Android identity, a fairness wrinkle); the only reason it was ever kept — an older no-ad-fill run — predated the Android-login + `yospace.pool=livepause` + channel/v2 path we run now. **Confirmed live 2026-10-03: breaks still fill (local + national) with it gone, working better than ever.** If a break ever comes back empty or 503s, `yo.lpa` is the first thing to restore. The pool `yospace.pool=livepause` stays — that's the one actually required (Yospace 503s without a session pool); whether `livepause` specifically is the app's pool or an inherited default is still unconfirmed, but it works, so leave it. (Also: ad **targeting** sends the device's **real** platform advertising id + `is_lat` + real DMA/consent, matching the app — see "Advertising-id capture" (added 2026-10-04). `android_id` is now only the last-resort fallback when no real ad id can be read.)

### Hard-won facts

- **Signing in as the Android TV app doesn't change the ad session.** Tested 2026-10-01 with DirecTV's device-code sign-in (`account/device/grant/v2/devicecode`, `clientId=UNIFIED_Android_TV_02`, approved at directv.com/tvsigninv2): CNN's `streamURL` came back identical to the web sign-in's (same host, `aegdfwprd01` profile and parameters). App client IDs: web `UNIFIED_DTV_WEB`, Android TV `UNIFIED_Android_TV_02`, Fire TV `UNIFIED_Android_TV`, Osprey/DirecTV boxes `UNIFIED_AEPS`. (As of 2026-10-02 we nonetheless sign in as Android TV end to end — now upstream's code sign-in, see "Sign-in, refresh and DRM recovery" above — for an honest, consistent client identity and a grant token that refreshes without a web re-login, **not** to change the ad streamURL, which this confirms it doesn't.)
- **`is_lat=0` with a device id is what gets local and political ads** (live A/B, 2026-09-28, CNN prime time). With `is_lat=1` (the account's web opt-out), breaks got national spots and 1:30–2:00 of "Commercial Break In Progress" slate. With `is_lat=0` and the device's own id, the same account got neighborhood ads (a local martial-arts school, Bob's Discount Furniture, Volvo Cars Ramsey, NY political ads) and short slates. `android_id:` did this on both a Fire TV and a Google TV (so it's a safe last-resort fallback); as of 2026-10-04 we send each device's **real** advertising id when it can be read (see "Advertising-id capture"), which is what the app does.
- **The advertising id over adb, by platform** (confirmed 2026-10-04, superseding the old "can't be read" note): **Fire OS** exposes it and `limit_ad_tracking` as secure settings (`settings get secure advertising_id`, no root) — read silently. A **GMS** device (Google TV/Shield) keeps the GAID in Play services: not in settings, not in `dumpsys`, no content provider, and a shell can't bind the GMS ad-id service (AMS blocks a non-app caller, so an `app_process`/dex read fails with `Unable to find app for caller`; a helper APK would work but isn't shipped). So on GMS it's read once off the device's own **Ads settings screen** (uiautomator, ~3 s flash). `android_id:<Android ID>` is the last-resort fallback when neither works. `limit_ad_tracking=1`, a deleted id, or an all-zero id all give the opt-out form. See "Advertising-id capture".
- **The 7 kHz ad audio is in DirecTV's ad files,** whatever the flags. National ads are part of the channel's live encode and are full range; inserted ads come from DirecTV's per-creative transcode, and many of their AC-3 renditions are band-limited.
- **DAI doesn't change picture quality.** Blockiness and blur measured the same across DAI configurations on the same content.
- **Don't forward the stick's raw `Dalvik/...` User-Agent to Yospace.** Tried 2026-09-28 (the bridge's server-side master fetch sent the Fire TV's `Dalvik/... AFTKRT` UA instead of python-requests'). Different from the app UA the patch sends now (see above). It did not fix the 7 kHz AC-3 ads (the encode is fixed per ad file, the same for every viewer), and the next break served wrong-market local ads (a St. Louis Kia dealer for a DMA 501 account). Reverted.
- **Settled 2026-10-02: the Osprey plays the same 7 kHz AC-3 ad files.** On CNN the Osprey opens a Yospace Pause Live session (Yospace SDK 3.11.2, `d=osprey`, `yo.cps=b.lp.d.y.224-3630.0x.s.n`, `yo.po=32`, `yo.aal=true`, same `cps.7950` profile). Its logcat (`VSTB load started for URL`) showed it loading `yospace01-directv.akamaized.net/dtv-prd/<id>/02001/u-6600-c-384-1-N.mp4` for two inserted ads; every segment decoded to 7.0–7.1 kHz in both ffmpeg and Apple's AudioToolbox Dolby decoder, and the user confirmed they sounded muffled on the Osprey too. The same ad's AAC rendition (`u-6600-a-96`) decodes full range. Nothing in the request (identity, User-Agent, channel/v1 vs v2, HEVC fields) changes which ad file is served. (The `CHANNELS="2"` stereo-downmix tried to dodge this on the bridge's decode side — removed 2026-10-03, see "Removed: stereo downmix" above — because live it only changed loudness, not the high end, confirming the muffle is this per-ad AC-3 encode in DirecTV's files, not the stick's downmix.)
- **The 7 kHz ads are in DirecTV's ad files.** Each inserted ad has one AC-3 and one AAC encode at a fixed CDN path; many ads' AC-3 encode is band-limited to ~7 kHz while their AAC is full range. No request flag or header changes which file is served. On the stick, an inserted ad shows as a switch from the secure to the non-secure video decoder (EventLogger `videoDecoderInitialized`). To check an ad: its segments on the ad CDN are unencrypted; decode the AC-3 `u-6600-c-384-1-N.mp4` (raw AC-3 frames start at `mdat`) with ffmpeg or `afconvert` and measure.
- **`d` is what the ad server keys on.** Same account, same breaks, run side by side:
  - no `d`: **0** inserted ads;
  - `d=android_tv`, `firetv`, `osprey` or `desktop`: ads inserted;
  - `androidtv`, `aft`, `atv`: 0 (not recognized).

- With `d=android_tv` the user gets local NYC ads (DMA 501) with normal audio.
- `smoke_test.py` asserts `d=android_tv`, the Android TV Nielsen/comScore values, `metr=1071`, no `us_privacy`, and no desktop flags.

### How the values were found (reproducible)

- **Web client:** HAR captures of stream.directv.com. The desktop request has 37–38 parameters. Its JS bundle (`att-purern.*.bundle.js`) contains DirecTV's shared player code with a per-platform ad-flag table (`paramOptions`: `DEVGRP_*`, `ADID_PREFIX_*`) and `metrParam {tv:1071, phone:47, tablet:47}`.
- **Osprey** (`com.att.tv.openvideo`, native Android):
  - `assets/config_servers/prod/AndroidNGC_OSPREY/AppConfiguration.json` → `payload.clientConfig.dai` (`deviceList[{device_type:osprey, dai_device_type:osprey, nielsen_dev_group:devgrp,STV}]`, comScore `OTT`/`a`, `metr 1071`, `attnid`, …);
  - the request builder is `com.att.ott.common.playback.player.quickplay.vstb.YospaceRequestParamGenerator` (decompile with `jadx`).
- **Android TV** (`com.att.tv`, React Native, Hermes bytecode in `assets/index.android.bundle`):
  - decompile with `pip install hermes-dec` → `hbc-decompiler index.android.bundle dec.js` (~80 MB);
  - `yospaceParameters` sets `d='android_tv'` for non-handset, non-tablet Android;
  - `universalYospaceParameters` sets `comscore_platform = systemName.toLowerCase()`, omits `us_privacy` when it's `'null'`, and adds `bZipCode` only when `cgnatEnabled` is on.
- **DirecTV's runtime config** (`api.cld.dtvce.com/ux/client/config/v3/client/config2?version=&deviceName=Phoenix&env=prod&applicationId=1`) needs a signed-in client, and returns config for the app the token was issued to. **Fetching the Android TV version would mean signing in as that app. Don't.** This is the one unverifiable gap: DirecTV may push extra Yospace tuning flags at runtime.

## Delivery and quality findings (measured)

- **The video bytes are identical** for DAI and non-DAI, whether direct or through the FastChannels relay, and on every CDN host (Fastly `-ms`, Akamai `-os`, CloudFront `-sponsored…cf.dtvcdn.com`, Cloudflare `-os.live.cflare`). SHA-256 matched every time.
- **CDN speed is about the same:** 31–35 Mbps and ~190–235 ms time to first byte from the LAN. DAI streams usually ride the `sponsored` route. The top 1080p rung needs 6.5 Mbps.
- **Since 2026-09-28 DAI takes the relay path too** (`yospace.com` is on the relay allowlist). Before that, DAI bypassed the relay, which was the only code difference between DAI and non-DAI delivery.
- **The main difference was the path** (before 2026-09-28):
  - with DAI, the stick fetched straight from the CDN, because Yospace hosts weren't on the relay allowlist;
  - without DAI, the bridge hands the stick `browser.m3u8`, and every playlist and segment goes through FastChannels' `browser-asset` relay.
  - The user saw non-DAI-through-the-relay as softer; direct non-DAI looked as good as DAI. This isn't proven numerically.
- **What DAI really provides:** local ads in the slots that are otherwise filler ("interdimensional cable"), the normal DirecTV client path, and an honest identity. Not better pixels.
- **Fire TV bridge picture:** set Color Format to **YCbCr, 8-bit**. The wrong setting lifts blacks and exposes blocking.
- **Audio:**
  - DirecTV's decoded AC-3 measures ~**−32 to −36 LUFS** integrated on dialogue-heavy windows, with **solid dynamic range** (music peaks well above that). **This is normal for decoded AC-3, not a deficit.** The stream's dialnorm normalizes dialogue to AC-3's **−31 dBFS reference**, so the decoder output is *meant* to sit near −31 and the AVR makes up the rest — it sounds plenty loud at a normal receiver setting (confirmed by ear, AVR ~33). **An earlier note here called this "~10 dB below normal TV" — WRONG:** that compared the decoded output to the −24 LKFS *transmission* standard, the wrong reference. Don't chase an absolute-loudness "fix"; there's no deficit, and a makeup gain would also flatten the good dynamics.
  - The inserted AAC ads measure ~**−20.6 LUFS** — genuinely hotter than the programming — so `dtv_aac_gain` cuts them **−12 dB** (8 × 1.5 dB steps, `_DEFAULT_STEPS`) down to the content level. That's a **relative** match (dialnorm-independent) and is the real fix for ads blasting over content; absolute loudness was never the problem. Measure a stick's feed (`http://<linkpi>:8090/stream<N>`, per ah4c `settings.json`) with `ffmpeg … -af ebur128`; for stereo-ness use mid/side (SIDE = L−R) + `aphasemeter` correlation — the 2ch AC-3 Lo/Ro reads as genuine stereo whose width tracks content (news desk ~corr 0.84/narrow, South Park ~0.48/wide).
  - **Loudness is set on the LinkPi gain, not in the stream** (the content AC-3 is DRM-encrypted, so the relay can't touch it). With the stereo-downmix feature removed (stock 5.1 AC-3 — see "Removed: stereo downmix"), box 16 at LinkPi **+12 dB** lands at **−23.9 LUFS** (broadcast −24), true peak −10.3 dBFS — clean, ~10 dB headroom (verified 2026-10-03). An earlier +6 "distorted" only because the old `CHANNELS="2"` downmix had made the feed hotter/brighter; stock + +12 is clean. Recommended operating point: **stock AC-3, raise loudness on the LinkPi (+12), let the ad cut keep breaks matched.**
  - Muffled/"AM radio" moments were bad ad files (see above), channel audio (MS Now had a dull stretch on both tracks and every box), or a stuck player app, which a reboot fixed.
- **When comparing boxes,** each DAI session gets its **own** ads and a different delay behind live. Compare only non-ad content, or align frames by content, and swap boxes to rule out hardware.

## Operating notes

- **Clear the DirecTV stream cache** after any flag change (cached Yospace URLs live 55 minutes):
  ```
  docker exec fastchannels sqlite3 /data/fastchannels.db "UPDATE source_cache SET value='{}' WHERE cache_key='directv_playback' AND source_id=(SELECT id FROM sources WHERE name='directv');"
  ```
  Toggling DAI in the UI also clears it.
- **Check what a server sends:** `curl -s -D - -o /dev/null http://<server>:5523/play/directv/<ccid>.m3u8 | grep -i location` and parse the query. Look at keys and constant values only; the URL carries session tokens.
- **Check a stick's quality level:** `adb shell dumpsys SurfaceFlinger | grep -A1 "SurfaceView - com.fastchannels"` shows the decode size.
- **Count inserted ads:** poll a DAI session's AC-3 audio playlist. Segments not on a `dfwlive-*` host are inserted ads, served unencrypted from `yospace01-directv.akamaized.net`.
- **Never pull or log bearer or play tokens** into chats or logs. Field names only.
- **`:latest` updates** when a scheduled build (every 6 hours) sees a new upstream `main` commit, Player APK or patch change. Rollback is a pin to `:upstream-<sha>` or `:build-<key>`.
